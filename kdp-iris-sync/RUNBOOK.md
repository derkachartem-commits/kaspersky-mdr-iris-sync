# KDP → IRIS: рабочие процедуры

Шаблоны кейсов в IRIS: **Cases → New case → Case template**.
- `kdp_anomaly_watch` — «KDP — Аномалия: наблюдение» (7 задач)
- `kdp_ddos_response` — «KDP — DDoS-атака: реагирование» (10 задач)

Эскалация из алерта — вручную: аналитик открывает алерт и создаёт кейс по нужному шаблону.

---

## 1. Аномалия (наблюдение)

Триггер: алерт `[KDP] Аномалия — <ресурс> (<check_name>)`, статус New.

1. Проверить доступность сервиса — HTTP 200, latency, error rate, health-check. Записать значения.
2. Сверить метрики с KDP — параметр, текущее значение, порог, превышение %. Убедиться, что рост реальный, а не сдвиг базовой линии.
3. Оценить динамику — растёт / плато / спад.
4. Проверить соседние сервисы на том же канале/ресурсе.
5. Зафиксировать вывод в кейсе (наблюдаем / ложное срабатывание / эскалация) с метриками и скриншотами.
6. Эскалация при ухудшении — создать кейс по шаблону «KDP — DDoS-атака» и связать.
7. Закрыть после `anomaly_stop` в KDP или при подтверждённом ложном срабатывании.

Критерий эскалации: превышение растёт, длительность > 15 минут или есть деградация сервиса.

---

## 2. Атака (реагирование)

Триггер: алерт `[KDP] Атака — <ресурс> (<вектор>)`, severity High/Critical.

1. Подтвердить атаку — вектор, пик bps/pps/rps, длительность, атакованные IP (из алерта и комментария коннектора).
2. Проверить доступность сервиса — HTTP 200, latency, error rate, доступность из внешней точки.
3. Проверить режим фильтрации KDP — always-on / on-demand; при on-demand включить, при необходимости усилить правила.

### Если сервис недоступен

4. Постоянная фильтрация (scrub) — перевести ресурс в always-on, проверить восстановление.
5. Поддержка KDP — тикет/эскалация по SLA, передать вектор и пики, запросить ручную настройку.
6. Резервирование — резервный канал/площадка, DNS failover (если предусмотрено схемой).
7. L7-защита — rate limit / WAF, отсечение L7-флуда, режим «только критичный трафик».

### Общее

8. Уведомить дежурного, владельца сервиса и бизнес по матрице эскалации; зафиксировать время.
9. Вести таймлайн — каждое действие комментарием с временем; при длительной атаке обновления каждые 30 минут.
10. Закрыть после `attack_stop` / `attack_short_term` в KDP и восстановления метрик; в резолюции — что сработало и что улучшить.

---

## Что делает коннектор сам

- создаёт алерт по событию KDP (source `Kaspersky KDP`, теги `kdp`, `kdp:attack|anomaly`, `svc:<ресурс>`);
- закрывает алерт при `*_stop` / `attack_short_term` с комментарием (длительность, пик);
- кейсы **не создаёт** и не закрывает — только человек.

## Метрики на дашборде коннектора

`127.0.0.1:8088/healthz` → `pull.last_success`, `pull.last_error`, `pull.last_stats`.
Если `last_success` старше 3 интервалов опроса — поток событий сломан, аномалии/атаки могут не приходить.
